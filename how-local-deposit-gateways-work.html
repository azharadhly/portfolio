How a local deposit gateway works

Not every customer pays by card. Many send a local bank transfer, and someone then has to match each transfer to the right person. My Local Depositor (MLD) turns that whole job into an API. Here is how version 2 of it fits together.

01The pieces

MLD’s merchant API lets a business create deposits and withdrawals in any currency its account is enabled for, track their status and get told when money arrives. A few terms carry the whole design:

  • Collection account. A bank account the customer pays into. GET /v2/collection-accounts lists the active ones.
  • Reference number. An 8-character code such as 7KQ2M9XA that the customer quotes on the transfer, so the money can be matched to the right deposit. It comes from GET /v2/quote, lasts one hour and works once.
  • Slip. The customer’s proof of payment: a JPEG, PNG or PDF of up to 5 MB.
  • Deposits and withdrawals. Money in and money out. Each has a ULID id and a status the merchant can look up at any time.

02Two ways to take a deposit

Hosted checkout. The merchant creates the deposit without a slip and sends the customer to the checkout_url it gets back. That page shows where to pay and collects the slip. Until then the deposit is awaiting_payment, and it expires when the hour runs out.

Host-to-host. The merchant collects the slip in its own app and includes it in the POST /v2/deposits request. The deposit starts as customer_claims_paid, never expires unpaid and can’t be cancelled. These requests should carry an Idempotency-Key header: sending the same key again returns the original response instead of creating a second deposit.

Why the reference number mattersA bank transfer shows up as an amount, a date and whatever the sender typed. The reference number is what ties that line on a statement to one deposit, and the API can search by it: GET /v2/deposits?ref_no=7KQ2M9XA.

03Signing every request

Every call carries three headers: X-Client-Id, X-Timestamp in Unix seconds, and X-Client-Signature. The signature is an HMAC-SHA256 of four parts joined with dots: the timestamp, the HTTP method, the path and a SHA-256 hash of the raw body. The key is a signing secret the merchant portal shows only once.

MLD rebuilds the same string and compares. A wrong signature gets 401 invalid_signature. A timestamp more than 300 seconds away from MLD’s clock gets 401 stale_request, so a captured request can’t be replayed later.

04The life of a deposit

A deposit always has exactly one status, and only a few moves between them are possible.

  • awaiting_payment is the only status that can be cancelled, with POST /v2/deposits/{ulid}/cancel.
  • customer_claims_paid means the customer says they paid and a slip is attached. It waits for review.
  • confirmed, shortpaid, overpaid and rejected are the outcomes of that review.
  • already_approved and already_rejected close a deposit that duplicates another one, which duplicate_of points to.

05Webhooks, verified

When an admin confirms a deposit, MLD sends a deposit.confirmed webhook, and payouts send events such as payout.processing. Each one is signed: the X-Signature header holds an HMAC-SHA256 of the timestamp and the raw body. The receiving server should:

  1. Verify the signature against the raw body, using a constant-time comparison.
  2. Reject old timestamps, outside a window of about 300 seconds.
  3. Skip duplicates by remembering each X-Event-Id.
  4. Answer with any 2xx. Anything else is retried with backoff.

It’s the at-least-once delivery from Note 02 again. If webhooks stop arriving, the docs suggest polling GET /v2/deposits/{ulid} instead.

06Paying out

A withdrawal sends money to a customer’s bank account or e-wallet. The merchant posts the exact amount the customer should receive, plus the bank, account number and account name. It moves from pending to processing to completed, or ends as rejected or cancelled. For LKR the only fee is a percentage service charge billed to the merchant on top, so the customer receives the full amount.

07Beyond LKR

The same endpoints handle other local currencies. GET /v2/currencies describes each one: minimum and maximum amounts, decimal places, which customer details are required and which payment methods or banks are available. The customer pays on the checkout page by bank account, QR code or payment link. For these deposits the response also shows received_amount, what actually arrived, and received_net, what is credited after the service charge. GET /v2/rates gives live buy and sell rates.

08The API at a glance

All paths sit under /api.

GET/v2/pingCheck that keys and signing work
GET/v2/currenciesCurrencies, limits and required fields
GET/v2/quoteReserve a reference number (LKR)
GET/v2/ratesLive buy and sell rates
POST/v2/depositsCreate a deposit
GET/v2/deposits/{ulid}Check one deposit
POST/v2/deposits/{ulid}/slipAttach or replace the slip
POST/v2/deposits/{ulid}/cancelCancel while awaiting payment
POST/v2/withdrawalsCreate a payout
GET/v2/withdrawals/{ulid}Check one payout

09Words to know

Reference number
An 8-character code the customer quotes on the transfer so it can be matched.
Collection account
The bank account customers pay into.
Slip
The customer’s proof of transfer, uploaded as an image or PDF.
Hosted checkout
MLD’s own payment page, reached through the deposit’s checkout_url.
Host-to-host
The merchant sends everything, slip included, straight from its own server.
HMAC-SHA256
A hash keyed with a secret, so only someone holding the secret can produce it.
Idempotency-Key
A header that makes a repeated request return the first result instead of acting twice.
ULID
A unique id that also sorts by creation time.

Based on the public My Local Depositor API v2 reference. Example values are made up.
